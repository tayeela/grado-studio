# План дальнейшей работы (08.11.2026)

Запрос владельца 08.11.2026: «сделай план дальнейшей работы; нужно учесть дальнейший переход на rust, идеальные стили
линий и полигонов; в идеале должно выглядеть так: пользователь выбирает территорию и ему сразу собираются листы по
видовым окнам, которые он настраивает». Владелец сам ничего не выбирает: ниже везде решение по умолчанию.
Состояние на старте — v0.99.136 (main), `rust/README.md`, PR #173–#181.

## Цель одной фразой

Выбрал территорию → данные пришли с нашего сервера уже оформленными → свои виды (рамки) сами встали на территорию →
готовые листы собраны → PDF и PPTX, где на бумаге ровно то, что на экране.

## Что уже есть

- Rust: `compute` (ТЭП, бит-в-бит, 84× быстрее), `geom` (по допуску), `plate` (пластина карты на tiny-skia),
  мост `grado_rs` (PyO3). Пластина уже в PDF «Макета листа» и в тяжёлых слайдах PPTX; PDF альбома — ещё вектор.
  Колёс `grado_rs` для Mac/Windows/сайта нет: сайт и установщик Rust пока не видят.
- Стили: единое / категории / диапазоны / правила; у класса полный знак (заливка, штриховка, контур, тип линии, подпись);
  знаки ЛГР REDLN97 на линиях и полигонах (знаки внутрь); 7 узоров штриховки, 4 типа линии.
- Листы: вид = слои + рамка на карте (#119), пустой лист, блок «Карта» выбирает вид, легенда идёт за видом, рамки листов
  альбома — те же рамки. Территория — роль слоя (`territory`). Ночная выгрузка ГИС ОГД и ЕГКО на сервер.

## Чего не хватает до цели

1. Рамки не встают на территорию сами: каждую тянут руками, листы под виды создаются по одному.
2. Экран (OpenLayers) и печать (Python → Rust-пластина) рисуют стиль двумя разными кодами — расходятся в мелочах.
3. Стиль — плоский набор полей. Нельзя «линия + знаки + стрелка», «заливка + штриховка + второй контур», знак вдоль
   линии своим шагом, штриховка в мм бумаги. Стиль из QGIS не переносится.
4. Альбом ППТ КРТ живёт своим движком рядом с листами.

## Шаги (по порядку, каждый — свой PR в `team/t60`, выкладка по готовности)

### Шаг 1. Колёса `grado_rs` везде (короткий, разблокирует остальное) — сделано в v0.99.137, кроме `GRADO_COMPUTE=rust` по умолчанию
- CI `rust.yml`: maturin-колёса macOS arm64 и x86_64, Windows x64, Linux (сайт); кладутся в релиз и в `requirements`.
- Установщик и сайт ставят колесо; без колеса — Python, как сейчас.
- `GRADO_COMPUTE=rust` по умолчанию после зелёной сверки `parity/` в CI.
- Готово, когда: `/api/health` сайта пишет `grado_rs: да`, пластина работает на сайте.

### Шаг 2. Одна модель стиля — «слои знака», как в QGIS
Решение по умолчанию: берём устройство знака QGIS (Symbol → Symbol layers), потому что владелец работает в QGIS
и это проверенная модель; формат храним в JSON проекта.
- Знак = стопка слоёв снизу вверх. Виды слоёв:
  - полигон: заливка; штриховка линиями (угол, шаг и толщина в мм бумаги, цвет, смещение); заливка точками/значками;
    контур (любой линейный слой ниже); сдвиг внутрь/наружу (полоса вдоль границы, как у ЗОУИТ);
  - линия: простая (толщина в мм, цвет, тип: штрихи в мм, концы, стыки); знаки вдоль линии (значок, шаг, смещение,
    поворот по линии, сторона — внутрь/наружу для полигона); штрихи поперёк (гребёнка); стрелка; знаки ЛГР REDLN97 —
    частный случай «знаки вдоль»;
  - точка: значок (SVG), круг/квадрат, подпись.
- Классификация (категории, диапазоны, правила) назначает классу **целый знак** (стопку), а не поля поверх слоя.
  Нынешние `st.cat.sym` и правила переводятся в стопку автоматически, старые проекты открываются как были.
- Размеры — в мм бумаги при масштабе листа (на экране пересчёт по текущему масштабу), как в QGIS «мм на карте».
- Импорт стиля QGIS `.qml` (и экспорт): владелец переносит свои стили из QGIS в ГРАДО одним файлом.
  Читать `.qml` — XML, разбор свой, небольшой; неизвестные виды слоёв знака — пропуск с пометкой.
- Библиотека знаков проекта и общая (ЛГР, ЗОУИТ, Эталон, сущпол) — один каталог, из которого берут и «Данные»
  (автостиль при выгрузке), и «Свойства».
- Готово, когда: стиль ЗОУИТ «полоса вдоль границы + штриховка + подпись» и ЛГР собираются в окне «Свойства» без кода,
  `.qml` из QGIS владельца открывается и выглядит так же (сверка картинкой).

### Шаг 3. Один рисовальщик знака на Rust — для экрана и печати
- Новый крейт `rust/crates/symbol`: рисует стопку слоёв знака по геометрии (заливка, штриховка в мм, знаки вдоль линии
  со стороной, гребёнка, пунктир) на tiny-skia — его зовёт `plate` для PDF/PPTX.
- Тот же крейт собирается в WebAssembly (`wasm-bindgen`) и рисует слой на карте экрана внутри OpenLayers
  (свой `ImageLayer`/canvas-рендерер слоя). Подписи остаются векторными и на экране, и в печати.
- Итог: экран = PDF = PPTX по одному коду; сверка `parity/plate` расширяется на все виды слоёв знака.
- Запасной путь: без WASM (старый браузер) — нынешний стиль OpenLayers.

### Шаг 4. Территория → виды → листы сами («поток одной логики»)
Модель (без предзаданных шаблонов, владелец 11.10 и 12.10):
- **Территория** — роль любого слоя (уже есть) или участок по кадастровому номеру/адресу.
- **Набор видов** — то, что пользователь сам настроил: для каждого вида слои с оформлением, масштаб или «вписать
  территорию с полем N м», пропорции, лист (формат, где карта, легенда, штамп, надписи). Набор сохраняется у
  пользователя и переносится в другой проект — это его собственный набор, не встроенный шаблон.
- **Сборка**: при выборе территории каждая рамка вида встаёт по территории (середина = центр территории, размер — по
  масштабу или «вписать»); если территория не влезает в лист при заданном масштабе — вид сам делится на несколько
  листов (сетка рамок с перекрытием, как атлас QGIS) или берётся ближайший круглый масштаб — по настройке вида,
  по умолчанию «круглый масштаб».
- Для каждого вида сразу создаётся лист «Макета листа» с блоком карты этого вида, легендой (только то, что видно
  в рамке), масштабной линейкой и штампом; номер и название листа — из имени вида.
- Смена территории или правка вида пересобирает листы, ручные правки листа (сдвиг надписи, своя подпись) сохраняются.
- Проверка готовности перед выгрузкой: пустая карта (уже есть по пластине), слой не догрузился, подписи пересекаются
  (#59), легенда пуста — лист помечен «не готов», выгрузка не молчит.
- Данные — с нашего сервера (ночной кэш ГИС ОГД/ЕГКО), со своим стилем из библиотеки знаков (шаг 2); порталы
  напрямую — только если в кэше нет.
- Готово, когда: на копии проекта Мытищинская/Безобразово выбор территории за один клик даёт все листы набора, PDF и
  PPTX без ручной правки карт (#167).

### Шаг 5. Альбом ППТ КРТ — тот же поток
- Листы альбома = набор видов (правила альбома остаются: подписи, легенды, `album-rules.md`).
- Движок альбома становится набором проверок и правил подписи поверх общих листов; PDF альбома — через пластину.
- Только после настоящей пересборки Гольяново и Безобразово на Mac и постраничной сверки `album_check`
  (нужен poppler на Mac — ставим через Homebrew командой для владельца или сверяем PyMuPDF, как 08.11).

### Шаг 6. Дальше переход на Rust (по «удушающей змее»)
Порядок по выгоде и риску, Python остаётся эталоном до сверки каждой части:
1. геометрия сервера через `grado_rs` (вместо приближённого наложения, #71);
2. разбор и подготовка данных порталов (`core/connectors`: `reqwest` + `tokio`, те же паузы и ≤ 3 повтора);
3. модель проекта (`serde`), сохранение и проверка формата;
4. сервер на `axum` — когда пп. 1–3 на Rust и тонкий Python-слой ничего не делает;
5. оболочка программы для Mac и Windows на **Tauri 2** (Rust, MIT/Apache): тот же интерфейс Vue в окне, без браузера
   и без установки Python у пользователя; сайт остаётся как есть;
6. PDF: пластина уже Rust; текст поверх — `krilla` (движок PDF Typst) вместо своего писателя, когда остальное на Rust.
   PPTX (`python-pptx`) и DXF (`ezdxf`) остаются на Python, пока нет равной Rust-библиотеки.
Интерфейс остаётся на Vue 3 + dockview + Web Awesome (решение 08.10): Rust заменяет ядро и рисование, не экраны.
