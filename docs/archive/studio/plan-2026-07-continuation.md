## Контекст: почему именно эти пункты

Проект вели параллельно два ИИ-трека: свой (Claude — редизайн интерфейса, ревизия диалогов,
настройка подписей) и посторонний (ChatGPT/Codex — упаковка, деплой, надёжность, +75 коммитов).
14 июля состояние документации консолидировано (см. `CLAUDE.md`). Пункты плана — это (а) хвосты,
задокументированные как «известные ограничения» в обоих треках, (б) логичные продолжения
недавно сделанного (настройка подписей → их наложение), (в) гигиена, которая обычно откладывается
до первого инцидента (релизы без версионной истории).

Пункты НЕ пронумерованы по обязательному порядку — каждый независим, можно брать любой. В конце
раздел «Рекомендуемая последовательность», если нужен один ответ «с чего начать».

## A. Проверка новых каналов дистрибуции на реальных платформах

**Почему:** за последний трек добавлены четыре способа получить Студию (Windows-инсталлятор,
macOS DMG, Docker-облако, браузерная Pages-редакция), но независимого пользовательского
подтверждения (не автотестов) на каждый есть по-разному:
- Windows — есть формальный аудит со скриншотами (`docs/audits/2026-07-13-windows-release/`),
  плюс CI прогоняет собранный EXE на настоящем `windows-latest` раннере. Наиболее проверенный канал.
- macOS DMG, Docker-облако, Pages-редакция — проверялись только «изнутри» той же ИИ-сессии
  (описано в `docs/session-log-archive.md` как «полный контейнерный smoke» и т.п.), без отдельного
  аудит-документа и без взгляда человека или другой сессии.

**Что сделать:**
1. **macOS DMG** (можно выполнить прямо на этой машине, она Mac): собрать через
   `packaging/build_macos.py`, реально открыть `.app`, пройти путь пустой старт → демо →
   рисование → ТЭП → PDF/DXF → альбом, как в Windows-аудите. Проверить codesign
   (`codesign --verify --deep --strict`), место хранения данных
   (`~/Library/Application Support/ГРАДО Студия`), что второй двойной клик не плодит второй сервер.
2. **Docker-облако**: `docker build` + `docker run` локально, healthcheck, регистрация
   администратора (первый = admin), полный цикл ТЭП/PDF/DXF/альбом внутри контейнера, проверка
   security-заголовков и что локальный мост :8081/импорт-по-пути реально отключены при
   `GRADO_CLOUD=1` (не просто предполагаются отключёнными по коду).
3. **Браузерная Pages-редакция**: собрать через `packaging/build_pages.py`, открыть в браузер-пейне
   (без Python-сервера!), пройти демо/черчение/слои/варианты/автосейв в IndexedDB, скачать
   `.grado-web.json`, убедиться, что попытка PDF/DXF/альбома **честно** блокируется с понятным
   сообщением (не тихо падает).
4. По итогам каждого — короткий аудит-файл в `docs/audits/<дата>-<канал>/` в том же формате, что
   Windows (найденные дефекты, скриншоты, вердикт).

**Проверка успеха:** для каждого из 3 непроверенных каналов — самостоятельный аудит-документ,
воспроизводящий формат Windows-аудита, с конкретными «до/после» находками (или явным «дефектов
не найдено»).

**Риски/зависимости:** Windows-инсталлятор и его CI нельзя проверить вживую без Windows-машины —
этот пункт остаётся на доверии к уже существующему аудиту + CI до появления такой возможности.

## B. Разрешение наложения подписей объектов

**Почему:** на прошлой неделе добавлена настройка кегля/цвета/шрифта подписи объектов (поле,
кегль, цвет, семейство — и на холсте, и в печати). Но сам механизм отрисовки подписи (`draw()` в
`app.js`, аналогично text-op в `core/render/grado_render/scene.py`) кладёт текст **в центроид
каждого объекта независимо от соседей** — на плотной застройке (сотни зданий с этажностью)
подписи неизбежно слипаются друг с другом и с геометрией. Проверено: в коде нет ни одного
упоминания collision/overlap применительно к подписям.

**Что сделать (по возрастанию сложности — можно взять только первый шаг):**
1. **Минимум:** не рисовать подпись, если рядом (в радиусе кегля × длины строки) уже есть другая
   подпись того же слоя — простой greedy-алгоритм по экранным bbox уже отрисованных подписей за
   этот `draw()`-проход. Работает и на холсте (JS), и в PDF (scene.py) — нужно продублировать
   логику (или вынести общий алгоритм и вызвать с двух сторон, если архитектура позволяет).
2. **Средне:** пропускать подпись только если объект **мельче порога на экране** (мелкие в этом
   зуме здания на подложке из сотен объектов) — сохраняет подписи крупных объектов, убирает шум
   у мелких, зумозависимо.
3. **Полноценно (см. `docs/roadmap.md` → «После 1.0» → «label engine с разрешением коллизий»):**
   настоящий label-placement (сдвиг подписи от центроида к свободному месту, лидер-линия при
   необходимости) — по факту отдельная фича, не хвост текущей работы.

**Проверка успеха:** визуальный тест на слое зданий 800+ объектов (или реальный проект юзера,
`persist` заглушён) — до/после скриншот, подписи не наслаиваются друг на друга сплошным пятном;
то же в PDF-рендере.

**Файлы:** `apps/studio/web/app.js` (место рисования подписи полигона, там же где
`label_font`/`LABEL_FONTS`), `core/render/grado_render/scene.py` (`labels.append({"op": "text", ...`).

## C. Технический долг геометрии (задокументирован, не блокирует работу)

Четыре независимых пункта, каждый можно брать отдельно:

1. **Параметрика fillet теряется в JS.** Инструмент «Сопрячь» линеаризует скругление в точки на
   клиенте, дублируя логику ядра `core/geom` (`path.py`/`curves.py`) вместо единого источника
   истины. Из-за этого фаска не остаётся редактируемым параметром после создания (только точки).
   Юнификация — either JS зовёт ядро через отдельный API, либо параметрика fillet хранится и на
   клиенте аналогично дуге (`{cx,cy,r,a0,sweep}` уже есть для дуг — можно по аналогии).
2. **Пространственный индекс привязок не везде.** `app-snap.js` имеет грид-индекс
   (`snapIndex()`/`snapQuery()`), но не все операции его используют — часть привязок всё ещё O(N)
   по всем объектам. На больших проектах (30000+ объектов, реальный случай юзера) это заметный лаг
   при рисовании. Найти оставшиеся O(N)-проходы (`grep` по `state.features.filter`/`.forEach` в
   контексте курсора) и перевести на индекс.
3. **`srcKey`-дедупликация не переживает `.grado` round-trip.** Повторная выгрузка НСПД/OSM той же
   территории после сохранения-открытия файла проекта снова добавляет объекты (ключ дедупа живёт
   только в localStorage/state, не в модели `.grado`). Нужно решить, хранить ли `srcKey` в самой
   модели (влияет на схему `.grado`/GeoPackage) или явно принять ограничение и предупреждать юзера.
4. **МСК-калибровка только UTM37N (Снайдер).** Нет UI для выбора/калибровки зоны МСК под другой
   регион — если Студия когда-то понадобится не только для Москвы, это станет блокером.

**Проверка успеха:** для каждого пункта — отдельный юнит-тест, воспроизводящий проблему до фикса
и подтверждающий её отсутствие после; регресс существующих 350 тестов.

## D. Гигиена релизов — CHANGELOG и теги

**Почему:** при трёх активных каналах дистрибуции (Windows/macOS/Docker, скоро возможно
пользователи со всех трёх) нет ни `CHANGELOG.md`, ни системы тегов — есть один случайный тег
`v0.9.0-beta.8` (нужен только для паттерна CI `v*`). Пользователю негде посмотреть «что нового
между сборками», а будущему релиз-процессу не на что опереться для «сравнить с прошлым тегом».

**Что сделать:**
1. Завести `CHANGELOG.md` в корне (формат Keep a Changelog подходит) — начать с текущей версии
   `0.9.0-beta.40`, кратко (не как `docs/session-log-archive.md` — user-facing формулировки).
2. Тегировать релиз при следующем повышении версии (`git tag v0.9.0-beta.41` и далее) — систематически,
   не от случая к случаю.
3. Решить: CHANGELOG обновляется вручную при каждом релизном коммите, или автоматизировать
   (генератор из commit-сообщений — но учти, что часть коммитов ChatGPT-трека однострочные без
   тела, для user-facing текста этого будет мало, придётся писать руками).

**Проверка успеха:** `CHANGELOG.md` существует и описывает хотя бы последние 5-10 версий понятным
пользователю языком; следующий релизный коммит сопровождается и записью в CHANGELOG, и тегом.

## E. Данные — московские городские слои и продолжение каталога

**Почему:** `data.mos.ru`/`ehd.moscow` были недоступны из среды разработки на момент проверки
(TLS обрывается на syscall сразу после connect, вероятный гео/IP-фильтр — при этом НСПД, тоже
российский госресурс, отвечал 200). Это могло измениться (смена сетевых условий, VPN-конфигурации)
и стоит перепроверить, а не считать вечным блокером. Отдельно — каталог открытых геоданных
openSpData (bella-mir.github.io/openSpData) частично пройден (спутник Sentinel-2, рельеф,
административные границы через OSM) — можно продолжить остальными разделами каталога, если это
всё ещё нужно юзеру (POI, транспортная инфраструктура и т.п. — каталог не пройден целиком).

**Что сделать:**
1. Быстрая проверка доступности `apidata.mos.ru`/`data.mos.ru` заново (`curl`/`urllib` с тем же
   SSL-контекстом, что и остальные коннекторы) — если доступен, оценить требования API-ключа
   (регистрация, платность) прежде чем строить коннектор.
2. Если по-прежнему заблокирован — явно отложить, не тратить время.
3. Просмотреть оставшиеся разделы каталога openSpData на предмет актуальности для юзера (спросить
   явно, не додумывать — это открытый вопрос направления, не техническая деталь).

**Проверка успеха:** либо новый коннектор с тестами (по аналогии с `osm.py`/`terrain.py`), либо
явная фиксация «остаётся заблокированным» с датой перепроверки в `CLAUDE.md`.

3. **D (CHANGELOG + теги)** — дёшево, откладывать нет смысла, но не блокирует ничего другого.
4. **C (технический долг)** — по одному пункту, не спеша; ни один не горит, но каждый дальше

5. **E (московские слои / каталог)** — только если юзер подтвердит, что это всё ещё приоритет
   (уже было отложено один раз по объективной причине — блок сети).

## Общие правила при выполнении любого пункта (не забыть)

- Тесты — обязательный гейт перед коммитом (см. `CLAUDE.md`, правило 8), команда там же.
- **Никогда не тестировать live на реальном проекте пользователя** — `window.persist=()=>{}`
  перед любым интерактивным тестом в браузере, `reload()` после.
- Файл `CLAUDE.md` правит(ят) несколько ИИ-сессий параллельно — перечитать перед точечной правкой,
  если `old_string` не совпал (значит, кто-то уже изменил файл).
- После значимого изменения — запись в `CLAUDE.md` → «Правки этой сессии» (сверху), не в этот
  план-файл (он статичен, отражает точку на 2026-07-14).
