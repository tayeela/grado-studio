## 3. Предложение: «роли листа»

Принцип: лист объявляет не список слоёв, а роли и цель; слои выбираются из ранжированных кандидатов по данным рамки. Владелец меняет роль (вкл/выкл), источник.

### 3.1 Описание

```
ROLES = {
  roads:     { cands: [ {src:"egko.roads", test:cover>=.6}, {src:"yandex.hd_roads", test:cover>=.3} ], mode:"poly", out:"yandex.hd_roads" },
  buildings: { cands: ["egko.buildings", "nspd.buildings", "yandex.buildings"], test:any },
  water:     { cands: ["egko.water","osm.water"] },
  parcels, zouit, redlines, docs_ppt, ..., rail, stations, names_places, names_streets, admin_corner, genplan_zones
}
sheet = { id, purpose:"…", basemap, roles: { roads:{on:true}, buildings:{on:true}, water:{style:"fill"}, docs_ppt:{on:true}, … } }
```
- Тест покрытия считается на уже загруженных данных в рамке F (доля площади рамки или число объектов), результат кладётся в `resolved[sheetId][role] = {src, why, coverage}` и показывается рядом с листом («Дороги: ЕГКО, покрытие 83 %; запасной Яндекс 41 %»).
- Загрузка: из ролей листа выводится список ключей и рамка (вместо ручного `keys` + forEach); для запасных кандидатов тянется только если основной не прошёл (двухфазная выгрузка) или лист 3 использует `cover` по маленькому окну.
- Легенда выводится из resolved и фактически нарисованного (кодом уже часть сделана: seen/has). Единый помощник `drawn(role)` возвращает, есть ли объекты роли в рамке; все безусловные пункты легенды (застройка, участки, ГПЗУ) берутся оттуда.
- Окно Яндекса 40 км2: если рамка > окна, тест покрытия роли честно показывает долю (< порога) и выбор/предупреждение, а для станций (обязательная роль) расширяет окно, как отдельный дешёвый запрос по точкам.
- Переопределения владельца: `sheet.roles` в TPL_COND/carryHand (как `edits`/`photos`) переживают пересборку; хранится только отличие от шаблона: `{roads:{src:"yandex.hd_roads"}, buildings:{on:false}}`. Заменяет редактирование `keys` целиком.
- frozen-листы не трогаются (sheetSpec возвращает ready, tpl не создаётся).

### 3.2 Что остаётся фиксированным (правила владельца)

Состав и порядок листов 3–9; шапка и оформление; цвета и толщины (C_ROAD #b4b4b4, C_TERR, ВРИ-палитра, REDLN97, СЗЗ ГИС ОГД, подтопление «Хатминки», станции, кегли); порядок слоёв снизу вверх (3.13); одинаковые места подписей на листах одной рамки (поэтому подписи и препятствия считаются по роли и данным проекта, а не листа); обязательные подписи; «ничего не придумывать сверх образцов»: роли, которых нет в образце листа, включить нельзя (список допустимых ролей по листу фиксирован), меняется только источник и вкл/выкл разрешённых.

### 3.3 Риски миграции

- Проекты владельца хранят `keys/styles/only` в sheet и tpl.base: надо ввести `roles` как дополнение, сначала с точным повтором нынешнего набора (golden: SVG листов 3–9 на нескольких территориях до/после, tests/test_t80 и e2e), старые листы остаются «legacy».
- Изменение источника дорог меняет внешний вид (рис. ЕГКО против Яндекс), поэтому порог покрытия не должен менять выбор на готовых листах без согласия: на первом этапе только показ решения.
- Память WL_MEMO и перенос ключей в слой `yandex.hd_roads`: сначала переименовать в роль `roads` без смены данных.
- Двухфазная загрузка удлиняет сборку при портальных паузах (правило: без параллельных выгрузок, не более 3 повторов).

### 3.4 Порядок малых шагов (каждый заканчивается тестом)
