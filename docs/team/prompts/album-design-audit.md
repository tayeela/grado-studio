# Аудит оформления альбома (шаблон для руководителя)

Когда: после сборки альбома (PDF и PPTX), до слова «готово» владельцу, и по просьбе владельца «проверь оформление». Кто: руководитель сессии
собирает страницы и запускает агентов Haiku 5.5 (владелец разрешил 07.10.2026 много агентов Haiku для механической работы); каждый аудитор видит
свой лист, находит огрехи, руководитель сводит, повторы склеивает, правила выводит. Аудиторы **ничего не правят** — только читают картинки и пишут находки.
Запреты — `docs/team/prompts/BANS.md`; правила, по которым судят, — `docs/wiki/album-rules.md` и `docs/standards/albums/layout-qa.md`.

## 1. Подготовка (руководитель)

```sh
OUT=/tmp/grado-audit/<дата>; mkdir -p $OUT                       # PDF альбома — album.pdf
pdftoppm -r 110 -png album.pdf $OUT/page                        # целые страницы: page-01.png …
# плитки 3 × 2 для разглядывания мелочей; А3 альбомная при 220 dpi — 3638 × 2573 px, плитка 1213 × 1287
for n in $(seq 1 <число страниц>); do for r in 0 1; do for c in 0 1 2; do
  pdftoppm -r 220 -f $n -l $n -x $((c*1213)) -y $((r*1287)) -W 1213 -H 1287 -png album.pdf $OUT/tile-$n-$r$c
done; done; done
pdftotext -layout album.pdf $OUT/album.txt                      # текст страниц для аудитора текста
python3 tools/album_lint.py album.pdf --json > $OUT/lint.json   # автоматические проверки (раздел 5)
```

Нужен список листов в порядке выдачи: `docs/wiki/sheets.md` (таблица «Альбом … в порядке выдачи»). Образцы владельца для сравнения —
`docs/team/samples/2026-10-07/*.jpg`, шапка `docs/standards/albums/pptkrt-header.jpg`.

## 2. Задание аудитору листа (по одному агенту на лист; подставить {N}, {название}, {концепт})

> Ты аудитор оформления листа {N} («{название}», концепт {концепт}) альбома ППТ КРТ, формат А3. Ничего не правь и не запускай, кроме чтения файлов.
> 1. Прочитай `docs/wiki/album-rules.md` целиком (правила владельца; нарушать нельзя). Строку этого листа в `docs/wiki/sheets.md` и раздел 5 правил — особенно.
> 2. Открой инструментом Read: `{OUT}/page-{NN}.png` (вся страница) и шесть плиток `{OUT}/tile-{N}-00.png … tile-{N}-12.png` (левый верх … правый низ, мелочи видны только на плитках).
> 3. Пройди по списку категорий ниже и перечисли **все** огрехи оформления, которые ВИДИШЬ (не домысливай; на плитке не видно — не пиши). Цитируй видимый текст подписи, называй цвет и знак.
> 4. Для каждого огреха укажи правило, которое нарушено (`album-rules §раздел`, `lr N`), либо `НОВОЕ ПРАВИЛО:` и одной фразой в форме правила («Подпись … должна …»), если правила для такого огреха нет.
> 5. Запиши результат по одной JSON-строке на огрех в `{OUT}/findings-{N}.jsonl`, поля: `sheet`, `id` («{N}-01»…), `cat` (код категории), `sev` (P0, P1, P2), `where` (плитка и место, например «плитка 02, у правого края, около 30 % высоты»), `what`, `evidence`, `rule`, `fix`, `conf` (high, medium, low).
>    Важность: P0 — явный брак или ввод в заблуждение, который владелец заметит сразу (обрезанная или наложенная подпись, неверный знак легенды, нет границы территории, не тот цвет по правилу); P1 — заметная небрежность; P2 — мелочь.
>    Не больше 30 находок, самые важные; сомневаешься — `conf: low`. Одинаковые огрехи (например, десять наложений подписей) — одной находкой со списком мест.
> 6. Ответ: число находок по P0/P1/P2 и три главные, по одной строке.

## 3. Задание сквозному аудитору (один агент на весь альбом)

> Сравни листы между собой: открой все `{OUT}/page-NN.png`, затем плитки шапок (верхние ряды) и легенд. Найди расхождения оформления одного и того же элемента на разных листах и между листом и названием:
> шапка и заголовок (размер, перенос, номер листа), легенда (размер знаков 13 × 3 мм, шрифт, порядок), граница территории (цвет, толщина, пунктир, подпись «Проектируемая территория – N га»), масштаб и линейка, стрелка севера, подписи улиц, рек, районов, станций, цвета одной и той же зоны, вода, дорога.
> Проверь порядок и состав листов с тем, что просил владелец (`docs/wiki/album-rules.md` раздел 5; задачи #47, #48) и соответствие названия листа его содержимому. Результат — тот же формат JSONL, `sheet: 0` для сквозных, файл `{OUT}/findings-cross.jsonl`.

## 4. Задание аудитору текста

> Прочитай `{OUT}/album.txt` (и текст PPTX: распакуй `unzip -p album.pptx 'ppt/slides/slide*.xml'`, бери содержимое `<a:t>`). Найди: опечатки; кавычки (внешние «ёлочки», вложенные „лапки“); сокращения (ул., пр-д, бульв., ш., пер., просп., наб., пл., пос.); регистр; тире и дефисы; единицы (га, кв. м, тыс. кв. м), десятичная запятая; неразрывные пробелы («№ 2682-ПП», «1,66 га»); слово «район» там, где владелец его убрал;
> «территория рассмотрения» вместо «разрабатываемая территория»; дубли слов и строк; обрывки (лишний пробел, одинокий предлог в конце строки); несоответствие названия листа его содержимому. Формат тот же, `sheet` — номер листа, `cat: T`, файл `{OUT}/findings-text.jsonl`.

## 5. Автоматические проверки (без модели)

`tools/album_lint.py album.pdf` читает PDF и находит то, что считает компьютер: наложение слов друг на друга, текст за краем страницы и рамки, слишком мелкий кегль, дубли подписей рядом,
невшитые и чужие шрифты, растровые вставки с разрешением ниже допустимого. Ошибка линта — обязательная находка в свод.

## 6. Категории огрехов (`cat`)

| код | что искать |
|---|---|
| A1 | подписи налезают друг на друга, на знаки, на легенду, на выноску, на угловые надписи |
| A2 | подпись обрезана рамкой листа, краем карты, легендой, шапкой или штампом |
| A3 | подпись нечитаема: мелкая (меньше 2 мм высотой букв), нет белой обводки на пёстром фоне, слабый контраст, не тот цвет по правилу |
| A4 | подпись не на своём месте: вне своего объекта, у соседнего объекта, поперёк дороги, вверх ногами, район подписан не на своей территории |
| A5 | дубли и «рассыпанные» подписи: одна улица или река много раз подряд, одинаковые подписи вплотную |
| B1 | в легенде нет знака для видимого на карте объекта (цвет, штриховка, линия) |
| B2 | в легенде есть знак для объекта, которого на листе нет |
| B3 | знак легенды не совпадает с картой (цвет, штриховка, толщина, пунктир) |
| B4 | легенда: порядок, группы, перенос строк, обрезка, размер знаков, пустые группы, разная вёрстка на листах |
| C1 | масштаб и линейка: не тот масштаб, нет линейки или стрелки севера, масштаб не совпадает с заявленным |
| C2 | покрытие: схема не покрывает территорию с запасом, пустые поля, белые полосы у края, обрезанный снимок |
| C3 | граница территории: нет, не поверх всех слоёв, не тот цвет, толщина, пунктир; нет выноски «Проектируемая территория – N га» там, где она нужна |
| C4 | подложка: размытый снимок, шов тайлов, чужой слой, не та основа (белая вместо снимка и наоборот), маска района не по правилу |
| C5 | линии: толщины, типы (ЛГР, красные линии, СЗЗ), висячие концы, линии поверх подписей |
| C6 | заливки и штриховки: цвета зон не по таблице, шаг и угол штриховки, нечитаемое перекрытие |
| C7 | данные: объекты не на месте, лишние (шум OSM, лишние дороги), отсутствующие ожидаемые (станции, реки, участки) |
| D1 | шапка и заголовок: перенос, размер, выход за рамку, не соответствует содержимому |
| D2 | компоновка: блоки пересекаются, выравнивание, поля, «висящая» легенда |
| D3 | площадь: большие пустые места, карта слишком мелко, дисбаланс листа |
| D4 | единообразие: один и тот же элемент оформлен по-разному на разных листах |
| D5 | фотофиксация: кадры разного размера, номера и стрелки не совпадают с кадрами, нет подписей, нет ссылки на панораму |
| E1 | файл: шрифты не вшиты или подменены, чужие гарнитуры |
| E2 | PPTX: текст не живой (растр), выходит за рамку при подмене шрифта, порядок слоёв, размер файла |
| E3 | растровые вставки: разрешение ниже допустимого на А3 |
| E4 | порядок и состав листов не такие, как просил владелец |
| T | текст: опечатки, кавычки, сокращения, единицы, пробелы, слова, которые владелец запретил |

## 7. Свод (руководитель)

1. Склей `findings-*.jsonl` в `findings.jsonl`, убери повторы (одна причина на нескольких листах — одна находка со списком листов).
2. Сгруппируй по причинам: «подписи улиц», «легенда», «граница района», «шапка» … Для каждой причины одна строка: сколько мест, на каких листах, нарушенное правило или `НОВОЕ ПРАВИЛО`.
3. Выведи правила: каждый повторяющийся огрех превращается в правило в `docs/standards/albums/layout-qa.md` (проверка глазами и компьютером) и, если это решение владельца, — в `label-rules.md` и `docs/wiki/album-rules.md`.
   Что можно проверить компьютером — добавь в `tools/album_lint.py` или в тесты (`apps/grado2/tests`), чтобы огрех не вернулся.
4. Заведи задачу GitHub (метка `альбом`) с таблицей причин и числом мест; исправления — отдельными PR по причинам, не одним большим.
5. Проверка исправления — навык `album-verify`: пересборка на копии проекта, те же плитки, тот же аудит на тех же листах, находок меньше.
